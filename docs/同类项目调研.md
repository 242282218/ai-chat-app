# 同类项目调研

调研日期：2026-06-07

调研目标：为当前 Android 原生 AI 聊天工作台寻找可参考的同类型开源项目，重点判断哪些设计值得借鉴，哪些能力不应照搬，以及当前项目下一步更应该补强的方向。

## 当前项目定位

当前项目是原生 Android AI 聊天工作台，核心特征是本地优先存储、BYOK、多 Provider、OpenAI-compatible 聊天和图片生成、可选 Go Gateway 工具能力。它不是单纯 ChatGPT 壳，也不是完整本地推理平台。

因此对标项目优先级应按相似度排序：

1. Android 原生、Kotlin/Compose、本地优先、多 Provider。
2. 支持工具、记忆、技能、Agent workflow。
3. 支持 OpenAI-compatible 协议、图片或多模态。
4. 支持本地模型推理或手机端 API server。

## 重点参考方向

### 1. 会话和消息渲染必须把历史数据当成不可信输入

当前“点击会话闪退”这类问题，本质上不是单个 UI bug，而是聊天历史进入渲染链路时缺少容错边界。同类项目都强调本地历史、导入导出和多模态内容；这意味着历史数据一旦格式演进，就必须兼容旧枚举、旧 content、旧图片格式和异常 tool payload。

当前项目应该继续坚持：

- Room entity 到 domain mapper 不直接 `valueOf()` 崩溃，未知枚举要降级。
- 多模态内容用结构化 `MessagePart`，不要长期依赖 Markdown inline 图片。
- 图片、工具结果、引用卡片进入 Compose lazy list 时必须使用稳定且唯一的 key。
- 会话详情页要有脏数据回归测试，而不是只测新写入数据。

### 2. Provider 配置体验优先参考 GPT Mobile

GPT Mobile 的价值不是架构复杂，而是把 BYOK、多 Provider、自定义 API URL、自定义模型、本地历史边界讲清楚。当前项目已经支持 New API、自定义兼容接口、聊天 Provider 和图片 Provider 拆分，下一步应该补的是产品化配置体验。

建议落地：

- Provider 列表展示能力标签：`Chat`、`Image`、`Vision`、`Tools`、`Streaming`。
- Base URL 规范化结果可见，明确根地址会转成 `/v1`。
- 连接测试返回结构化错误：认证失败、模型不存在、endpoint 不兼容、网络超时。
- 图片 Provider 和聊天 Provider 独立配置时，在设置页用明确文案解释 key 可不同。

### 3. 工具和 Agent 能力优先参考 OneClaw，但收敛范围

OneClaw 和当前项目都走 Android 本地优先 + 工具能力方向，它最值得参考的是边界表达：工具注册、技能、长期记忆、会话摘要、权限和安全说明。当前项目已有 Go Gateway、search、sandbox 和工具历史，不缺“再加工具”的入口，缺的是协议稳定性和失败路径稳定性。

建议落地：

- 工具 manifest、search、sandbox、error response 建立跨端 golden fixture。
- Android 和 Gateway CI 同时监听 `contracts/gateway/**`。
- 工具结果进入聊天时只传短 ID，避免把长 JSON、日志或大文本塞进 navigation route。
- Gateway search 默认不要暴露 mock 结果；未配置真实搜索时应返回不可用。
- 工具失败、取消、超时都要持久化可读状态，不让 UI 根据半成品 payload 崩溃。

### 4. Compose 架构参考 skydoves，但不引入外部聊天服务

skydoves/chatgpt-android 对当前项目的主要参考价值是 Android 工程实践：模块边界、UI/data 分层、WorkManager、Baseline Profiles 和测试结构。它使用 Stream Chat SDK 是为了示例实时聊天系统，不符合当前项目“聊天内容本地优先、Provider 可替换”的方向。

建议落地：

- 继续保持 `feature -> domain -> data/provider/tool` 边界。
- UI 组件只消费 domain model 和 UiState，不直接依赖 Room entity 或网络 DTO。
- 聊天页复杂渲染拆成可单测的 mapper/key/source resolver。
- 对启动和聊天首帧性能补 Baseline Profile 或 Macrobenchmark，但优先级低于稳定性。

### 5. 本地模型能力只做长期储备

ChatterUI、HostAI、LLM Hub 都证明移动端本地推理和本地图片生成有用户价值，但当前项目的主要问题不是缺本地推理，而是 Provider/Gateway/多模态历史链路需要稳定。

建议暂不做：

- 暂不内置大模型运行时、模型市场或 HuggingFace 下载器。
- 暂不把 App 变成手机端 OpenAI-compatible server。
- 暂不做全离线 Stable Diffusion 图片生成。

可以先预留：

- Provider 类型中保留 `OpenAI-compatible` 路径，未来可接 HostAI/Ollama/LM Studio 等本地服务。
- 模型能力标签中预留 `Local`、`Vision`、`ImageGeneration`。
- 图片和文件附件继续用结构化 content parts，避免未来接本地模型时重做数据模型。

## 对当前项目的优先级建议

### P0：先把会话点击和历史数据稳定性闭环

- 为旧枚举、坏 JSON、旧 Markdown 图片、重复图片 URI、坏本地路径补回归测试。
- 所有聊天渲染入口遵循“失败显示占位，不让页面崩溃”。
- 抓到真实崩溃栈后，优先修 domain/data 边界，而不是只包 UI try/catch。

### P1：补 Provider 和图片生成的用户可理解边界

- 设置页明确区分聊天 Provider 和图片 Provider。
- 每个 Provider 显示支持的 endpoint 和能力标签。
- 图片生成失败要把 endpoint、HTTP 状态、Provider 错误 message 映射成用户可读状态。

### P1：补工具协议和 Gateway 安全边界

- `contracts/gateway/fixtures/` 增加 search、sandbox、error fixture。
- Android `GatewayClientTest` 和 Go `go test ./...` 同时读取或校验协议 fixture。
- Gateway 未配置真实搜索时不要返回 mock 搜索结果。

### P2：改善聊天体验，但避免扩大范围

- 长会话自动摘要可参考 OneClaw，但先做手动触发或后台维护，不要影响主路径。
- 多模型并行回答可参考 GPT Mobile，但会显著改变会话模型和 UI，建议排到 Provider 稳定之后。
- TTS、角色卡、本地模型、语音聊天暂不进入近期主线。

## 许可证和复用边界

- OneClaw：仓库标注 All rights reserved，只能参考产品和架构思路，不能复制实现。
- GPT Mobile：GPL-3.0，直接复制代码会带来传染性开源义务。
- skydoves/chatgpt-android：Apache-2.0，可参考代码结构，但要避免引入不必要的 Stream Chat 服务依赖。
- ChatterUI：AGPL-3.0，网络服务和分发相关义务更强，不适合直接复用。
- HostAI Android：Apache-2.0，可参考 API server 组织方式。
- LLM Hub：PolyForm Noncommercial，商业使用受限，只适合参考产品能力。

## 结论

最值得重点看的三个项目是：

1. OneClaw：参考 Android 本地优先 Agent、工具、技能、记忆和权限边界。
2. GPT Mobile：参考 BYOK、多 Provider、自定义模型和本地历史的产品体验。
3. skydoves/chatgpt-android：参考 Compose 工程结构、模块拆分、Baseline Profile 和 Android 架构实践。

当前项目不应该照搬任何一个项目的完整架构。短期最有价值的不是增加新能力，而是把历史消息、多模态图片、工具结果和 Provider 错误都当成不可信输入，建立可回归验证的稳定渲染链路。
