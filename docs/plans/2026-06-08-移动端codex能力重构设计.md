# 移动端 Codex 能力重构设计

日期：2026-06-08

状态：设计草案，等待确认后执行。

## 1. 目标

本次重构的目标不是把当前 App 做成“聊天壳”，而是把它重构成移动端 AI 任务工作台：用户可以在手机上发起任务，模型能规划、调用工具、搜索信息、运行代码、生成图片、读取授权文件、沉淀上下文，并把过程和结果可靠地保存到本地。

最终效果应接近 Codex 的核心能力，但适配 Android 手机形态：

- 能聊天，但聊天只是任务入口之一。
- 能调用工具完成任务，包括搜索新闻、运行短代码、生成图片、检查 Provider、读取用户授权文件。
- 能展示工具执行过程、权限确认、错误原因和可恢复建议。
- 能保留会话、工具结果、图片历史、配置和后续可扩展的技能/记忆。
- 使用 Android 原生友好的组件和现有技术栈，减少冗余依赖。

## 2. 约束和边界

### 2.1 许可证边界

参考项目只能用于 clean-room 设计：参考架构、职责拆分、数据流、交互和测试策略，不复制受限许可证源码。

- OneClaw：All rights reserved，只参考工具、技能、记忆、Agent 边界，不复制实现。
- GPT-Mobile：GPL-3.0，只参考 Provider 配置体验、协议拆分和状态流，不复制实现。
- ChatterUI：AGPL-3.0，只参考能力面，不进入近期实现。
- LLM Hub：非商业限制，只参考长期方向。
- chatgpt-android、HostAI Android：Apache-2.0，可参考工程结构和协议组织，但仍按本项目风格重写。

### 2.2 密钥边界

用户提供的测试 Key 只用于本地手动验证，不能写入代码、文档、测试 fixture、提交历史、日志或 CI 配置。

文档和代码中只允许出现：

- New API Base URL：`https://zzshu.cc`
- 图片生成接口路径：`/v1/images/generations`
- Secret 占位名：`NEWAPI_API_KEY`、`NEWAPI_IMAGE_KEY`

Key 必须通过设置页、Android Keystore 支持的 SecretStore、测试机环境变量或 GitHub Secrets 注入。

### 2.3 非目标

本轮不做以下内容：

- 不直接复制参考项目源码。
- 不引入 React Native、Stream Chat SDK、第三方聊天服务依赖。
- 不内置本地大模型运行时、模型市场或手机端 OpenAI-compatible server。
- 不做全量 Gradle 多模块迁移作为第一阶段目标。
- 不发布 Release、不升级版本号，除非后续明确要求。

## 3. 当前项目现状

当前项目已经具备较好的基础：

- Android：Kotlin、Jetpack Compose、Material 3、Room、Koin、OkHttp、kotlinx.serialization、Coil。
- Provider：OpenAI Responses、OpenAI Chat Completions 兼容接口、New API、Sub2 API、Custom、OpenRouter、Ollama。
- 图片生成：OpenAI-compatible `/v1/images/generations`。
- 工具：本地工具、Gateway 工具、工具确认、工具结果持久化、工具历史。
- Gateway：Go 标准库 HTTP server，已有 health、tool manifest、search、sandbox。
- 数据：本地优先，Room schema 当前 version 10，SecretStore 保存 API Key。

主要问题不是能力完全缺失，而是职责过于集中、协议边界不够清晰、任务视角不够强：

- `GenerationController` 同时做会话准备、Provider 选择、上下文压缩、工具循环、UI 状态和错误处理，后续扩展会越来越难。
- `ToolExecutor` 同时负责工具发现、设置过滤、Gateway 调用、本地工具、图片生成、错误映射和持久化，已经接近平台层，应拆出执行引擎边界。
- `OpenAiChatProvider` 同时承载 Responses、Chat Completions、工具、Hosted Web Search、多模态和错误解析，协议族应更明确。
- Chat 页面仍是主入口，任务、工具、技能、记忆缺少统一产品模型。
- Gateway 协议只有部分 fixture，search、sandbox、error、tool result 的跨端 golden 测试需要补齐。

## 4. 参考项目映射

### 4.1 OneClaw

采用思路：

- 工具系统作为独立平台层，而不是附属于聊天页。
- 工具契约、注册中心、执行引擎、权限、启用状态、超时和错误封装分离。
- Skill 用 `SKILL.md` 表达可复用提示词工作流。
- 记忆采用“写入、索引、检索、注入”的管线。

不采用：

- 不复制 OneClaw 源码。
- 不一次性实现 39 个工具。
- 不做 Telegram/Discord 等消息桥接。
- 不把 JS 插件系统作为近期核心目标。

### 4.2 GPT-Mobile

采用思路：

- 多 Provider 不做万能 DTO，而是“统一编排入口 + 各协议精确 DTO”。
- Provider 配置页展示能力标签、Base URL 规范化结果、连接测试结构化错误。
- 流式响应统一成语义事件，让 UI 不感知底层协议差异。

不采用：

- 不复制 GPL-3.0 代码。
- 不把项目收缩成纯聊天客户端。
- 不为多模型并行回答优先改会话模型。

### 4.3 chatgpt-android

采用思路：

- UI 单向数据流：Repository 输出状态，ViewModel 编排 UiState，Composable 只渲染和提交意图。
- 工程边界按 `core/data/feature` 或等价包结构收口。
- Baseline Profile 和构建检查保留为质量保障。

不采用：

- 不引入 Stream Chat SDK。
- 不为了形式拆很多 Gradle 模块。

### 4.4 HostAI Android

采用思路：

- OpenAI-compatible 协议要稳定，有健康检查、模型列表、SSE、结构化错误。
- 长连接、并发、超时、请求体大小和断连语义要显式设计。

不采用：

- 不把 App 变成手机端推理服务。
- 不内置 LiteRT 本地推理。

## 5. 方案取舍

### 方案 A：小修小补

保留现有结构，只在当前类中继续加工具、加 UI、加 Provider。

优点：

- 改动最小。
- 短期最快看到功能。

缺点：

- `GenerationController` 和 `ToolExecutor` 会继续膨胀。
- 工具、任务、技能、记忆会混在聊天链路里。
- 未来每加一个能力都会扩大回归风险。

结论：不推荐。只能用于紧急 bugfix。

### 方案 B：渐进式重构为移动端任务工作台

保留现有 app 单模块和核心依赖，先在包结构和契约层重建边界，再逐阶段移动实现。目标是让现有能力稳定迁移到新的 Agent/Tool/Provider 编排层。

优点：

- 风险可控，能逐阶段验证。
- 复用现有 Room、Provider、工具、Gateway 和 UI 基础。
- 不需要先做大规模模块迁移。
- 更符合当前项目“已有能力但需要架构收口”的状态。

缺点：

- 需要短期保留旧路径和新路径并行。
- 对迁移顺序要求高，必须每阶段有测试。

结论：推荐。

### 方案 C：全量重写为多模块 Agent App

一次性拆成多个 Gradle 模块，并重写 Chat、Provider、Tool、Memory、Settings、Gateway 客户端。

优点：

- 最终边界最干净。
- 模块依赖可以从构建层强约束。

缺点：

- 当前未提交变更多，直接大改容易覆盖已有工作。
- Room migration、UI、工具和 Provider 会同时变动，回归面过大。
- 很难在每一步保持可运行。

结论：暂不采用。等方案 B 稳定后，再按实际收益拆 Gradle 模块。

## 6. 推荐架构

推荐采用方案 B。

目标结构先以包边界落地，后续再判断是否拆 Gradle 模块。

```text
app/
  app/                  Application, Koin, dispatchers
  navigation/           App routes, draft handoff
  domain/
    model/              Conversation, Message, TaskRun, Tool, Skill, Memory, Provider
    repository/         Repository contracts
    usecase/            Pure business orchestration use cases
  data/
    local/              Room entity, DAO, migration
    mapper/             Entity <-> domain, JSON <-> domain
    repository/         Room/DataStore/SecretStore implementations
    settings/           Preferences and runtime settings
  provider/
    api/                Stable provider contracts and events
    openai/             OpenAI Responses protocol
    compatible/         OpenAI Chat Completions protocol
    image/              Image generation protocol
    http/               SSE, OkHttp clients, error body helpers
  agent/
    runtime/            TaskOrchestrator, model loop, tool loop
    context/            ContextBuilder, compactor, memory injector
    planner/            Task mode and prompt policy
  tool/
    model/              ToolDescriptor, schema, result, risk
    registry/           Built-in, Gateway, Hosted registry
```

第一阶段不要求物理移动所有文件，只要求新增代码遵守这个边界，并逐步把过大的类拆入目标包。

## 7. 核心运行链路

新的主链路以任务为中心：

1. 用户在 Chat 或 Task 入口提交请求。
2. `TaskOrchestrator` 创建或复用会话，生成 `TaskRun`。
3. `ContextBuilder` 收集系统提示、会话窗口、摘要、工具结果、图片和授权文件引用。
4. `ProviderRouter` 根据 Provider、模型能力和任务类型选择协议族与模型。
5. Provider 输出统一 `ProviderEvent`：文本、思考、工具调用、图片、失败、完成。
6. 工具调用进入 `ToolExecutionEngine`。
7. 高风险、网络、文件、执行类工具按策略要求用户确认。
8. 工具结果落库为 `ToolResult` 和 Tool message。
9. 有工具结果时回到模型继续下一轮，直到完成、失败、取消或达到深度上限。
10. UI 展示任务步骤、消息、工具卡片、图片和错误恢复建议。

关键原则：

- 模型负责规划，App 负责权限、安全、执行和持久化。
- 工具结果进入模型上下文时必须压缩成短文本或结构化摘要，长 JSON 不直接塞进路由或 UI 状态。
- 历史数据一律视为不可信输入，mapper 和 renderer 不允许因未知枚举、坏 JSON、坏图片 URI 崩溃。

## 8. Provider 重构设计

### 8.1 Provider 能力模型

Provider 配置和模型能力需要显式显示并参与路由：

- `Text`
- `Vision`
- `ImageGeneration`
- `ToolCalling`
- `HostedTools`
- `Streaming`
- `StructuredOutput`
- `LongContext`
- `Local`

设置页要展示 Provider 能力标签，模型列表也要显示模型级能力覆盖 Provider 默认能力。

### 8.2 协议族

Provider 协议不做万能 DTO，按协议族维护精确 DTO：

- `OpenAiResponsesProtocol`
- `OpenAiChatCompletionsProtocol`
- `OpenAiImagesProtocol`
- `OllamaOpenAiCompatibleProtocol`
- 后续预留 `AnthropicMessagesProtocol`、`GeminiGenerateContentProtocol`

统一的是上层事件：

```kotlin
sealed interface ProviderEvent {
    data class TextDelta(val text: String) : ProviderEvent
    data class ThinkingDelta(val text: String) : ProviderEvent
    data class ToolCallDelta(val call: ToolCall) : ProviderEvent
    data class ImageDelta(val image: MessagePart.Image) : ProviderEvent
    data class Failed(val error: ProviderError) : ProviderEvent
    data object Completed : ProviderEvent
}
```

当前 `ProviderStreamEvent` 可渐进迁移为上面的语义事件，先兼容旧名称，不做一次性替换。

### 8.3 New API 测试配置

测试时 Provider 配置应为：

- Base URL：`https://zzshu.cc`
- 规范化后聊天/模型接口根地址：`https://zzshu.cc/v1`
- 图片生成接口：`POST /v1/images/generations`
- 聊天 Key：通过 SecretStore 或本地环境 `NEWAPI_API_KEY`
- 图片 Key：通过 SecretStore 或本地环境 `NEWAPI_IMAGE_KEY`

验证要求：

- 设置页能保存聊天 Provider 和图片 Provider。
- 连接测试能区分认证失败、模型不存在、endpoint 不兼容、网络超时。
- 图片生成失败要展示 endpoint、HTTP 状态、Provider 错误 message 和恢复建议。

## 9. 工具系统重构设计

### 9.1 目标

工具系统要成为移动端 Codex 能力的核心平台层。

工具执行必须具备：

- 可发现：本地工具、Gateway 工具、Provider Hosted Tool 都进入统一目录。
- 可解释：每个工具有名称、描述、参数 schema、权限级别、风险等级和超时。
- 可控：按工具、风险、来源设置是否启用和是否每次确认。
- 可观察：每次执行持久化开始时间、结束时间、耗时、输入摘要、输出摘要、错误码。
- 可恢复：失败时给出结构化错误和下一步建议。

### 9.2 组件

```text
ToolRegistry
  - BuiltInToolSource
  - GatewayToolSource
  - HostedToolSource

ToolExecutionEngine
  - resolve descriptor
  - check enabled state
  - validate schema
  - request approval
  - run with timeout
  - persist ToolResult
  - return model-facing content

ToolApprovalController
  - high risk / network / file / execute policy
  - pending call editing
  - approve / deny / cancel
```

现有 `ToolExecutor` 应拆成：

- `ToolCatalogService`：工具发现、缓存、设置过滤。
- `ToolExecutionEngine`：执行流程控制。
- `GatewayToolRunner`：Gateway search/sandbox 调用。
- `LocalToolRunner`：本地工具调用。
- `ImageGenerationToolRunner`：图片生成工具调用。
- `ToolResultWriter`：结果持久化和错误映射。

### 9.3 工具范围

近期保留和完善：

- `time`
- `text_transform`
- `code_diff_preview`
- `web_search_local`
- `local_js`
- `file_read`
- `provider_connection_test`
- `image_generation`
- `web_search` via Gateway
- `code_sandbox` via Gateway

近期不做：

- 任意 Shell 执行。
- 自动读取任意本地路径。
- 后台自动执行高风险工具。
- 用户自定义 JS 工具市场。

### 9.4 Gateway 协议

Gateway 需要补齐协议 fixture：

- `contracts/gateway/fixtures/tool-manifest.json`
- `search-success.json`
- `search-error-unavailable.json`
- `sandbox-success.json`
- `sandbox-timeout.json`
- `sandbox-error-unavailable.json`
- `gateway-error.json`

Android 和 Go 都必须读取或校验这些 fixture。

Gateway 规则：

- Search 未配置真实 adapter 时返回 `search_unavailable`，不能返回 mock 成功。
- Sandbox 默认禁用网络、只读文件系统、资源限制、输出截断。
- 所有 API 错误保持结构化 JSON：`code`、`message`、`requestId`、`details`。
- Go error 必须带上下文。

## 10. Skill 设计

Skill 是可复用提示词工作流，不是可执行代码。

存储位置：

- 内置技能：`app/src/main/assets/skills/<name>/SKILL.md`
- 用户技能：`filesDir/skills/<name>/SKILL.md`

格式：

```markdown
---
name: code-task
display_name: 代码任务
description: 帮助模型按移动端工具能力完成代码相关任务
version: 1
tools_required:
  - file_read
  - code_sandbox
---

正文为给模型的工作流指令。
```

近期内置技能：

- `code-task`：代码解释、补丁设计、测试建议。
- `web-research`：搜索新闻、引用来源、汇总结论。
- `image-generation`：提示词澄清、尺寸和质量选择。
- `bug-diagnosis`：日志、错误、复现步骤分析。
- `refactor-planning`：重构设计、风险和验证清单。

Skill 加载方式：

- 用户通过 UI 选择。
- 用户在输入中使用 `/skill`。
- 模型通过 `load_skill` 工具请求加载。

第一阶段只实现内置技能和读取，不实现用户编辑器。

## 11. 记忆和上下文设计

近期目标是稳定上下文，不追求复杂向量检索。

阶段 1：

- 会话摘要：长会话超过阈值时生成 summary message。
- 置顶事实：用户可手动保存偏好、项目约束、常用 Provider。
- 工具摘要：工具长输出只保留短摘要进入模型上下文，原始输出留在 ToolResult。

阶段 2：

- `memory_item` 表：保存用户事实、项目事实、偏好、任务结论。
- `memory_index` 表：保存 chunk、source、updatedAt。
- 关键词检索优先，向量检索暂不进入近期主线。

阶段 3：

- 可选 BM25 或轻量本地索引。
- 若要引入向量模型，必须先证明收益，并评估包体、性能和机型兼容。

上下文构建原则：

- 当前任务 > 当前会话最近消息 > 会话摘要 > 相关记忆 > 工具历史摘要。
- 图片和文件只能使用用户授权来源。
- Provider 请求体中的内容 parts 必须结构化，不再依赖 Markdown inline image 作为主数据源。

## 12. UI 重构设计

### 12.1 信息架构

移动端第一屏应是可用的工作台，不做营销式首页。

推荐导航：

- `工作台`：任务入口、最近任务、继续未完成任务。
- `聊天`：普通对话和任务对话。
- `工具`：工具目录、工具设置、工具历史。
- `图片`：图片生成和历史。
- `设置`：Provider、Gateway、数据、主题。

如果底部导航项过多，可以把 `图片` 放入工作台快捷入口，底部保留 `工作台 / 聊天 / 工具 / 设置`。

### 12.2 任务页面

任务页面展示：

- 用户目标。
- 当前模型和 Provider。
- 执行步骤列表。
- 工具调用卡片。
- 等待用户确认的工具面板。
- 结果和引用。
- 可继续追问、重试、复制、导出。

### 12.3 聊天页面

聊天页面保留，但职责收敛：

- 输入文本、图片、文件授权。
- 展示消息、工具卡、图片。
- 不直接承载工具编排逻辑。
- Compose 只消费 `ChatUiState` 和回调，不能直接读 Room entity 或网络 DTO。

### 12.4 设置页

Provider 设置页需要补强：

- 能力标签。
- Base URL 规范化预览。
- Chat Provider 与 Image Provider 明确区分。
- 连接测试结果结构化展示。
- Key 不显示明文，只显示是否已保存。

## 13. 数据库和迁移

任何 Room entity、DAO、Database 改动必须：

- 递增 schema version。
- 新增 migration。
- 更新 schema JSON。
- 补迁移测试。

推荐新增表按阶段进入：

阶段 1：

- 不新增表，先拆逻辑和补测试。

阶段 2：

- `task_run`
- `task_step`
- `tool_result` 如现有表不足，再扩展现有 tool invocation 表，不重复建表。

阶段 3：

- `skill_definition` 或使用文件系统 + 索引表。
- `memory_item`
- `memory_index`

历史数据容错要求：

- 未知枚举降级，不崩溃。
- 坏 JSON 降级为文本错误卡。
- 坏图片 URI 显示占位，不崩溃。
- 重复 lazy key 必须有回归测试。

## 14. Codex 执行阶段

### 阶段 0：准备和防护

成功标准：

- `git status --short` 已检查。
- 当前未提交变更不被覆盖。
- 现有测试能跑或明确已有失败。

任务：

## 16. 成功验收标准

功能标准：

- 用户能在手机上完成普通聊天。
- 用户能让模型调用搜索工具获取新闻并返回来源。
- 用户能让模型运行短 Python 代码并解释结果。
- 用户能通过图片生成工具或图片页生成图片。
- 用户能查看工具调用、参数、状态、耗时、失败原因。
- 用户能停止生成，停止后已有内容和状态被持久化。
- Provider 和 Gateway 未配置时显示可理解错误，不崩溃。

架构标准：

- Compose 不直接依赖 Room entity、网络 DTO 或 Gateway JSON。
- Provider 协议 DTO 按协议族组织，不做万能 DTO。
- 工具执行流程有独立引擎和持久化边界。
- 高风险工具默认需要确认。
- API Key 不入库明文、不进备份、不进日志、不进仓库。

质量标准：

- Android 相关单测通过。
- Gateway `go test ./...` 通过。
- Room migration 有测试。
- Gateway fixture 有双端覆盖。
- 历史坏数据渲染不崩溃。

## 17. 风险和应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 许可证误用 | 代码无法安全分发 | 只参考设计，不复制受限源码 |
| 密钥泄漏 | 安全事故 | Key 只进 SecretStore、环境变量或 GitHub Secrets |
| 大重构破坏主路径 | App 不可用 | 阶段式迁移，每阶段可运行可测试 |
| 工具误执行 | 用户数据或环境风险 | 风险分级、确认策略、文件授权、Gateway 沙箱 |
| Room 迁移失败 | 用户数据损坏 | migration + schema + 测试 |
| Provider 兼容差异 | New API 或自定义接口失败 | 协议族 DTO + 连接测试 + 结构化错误 |
| 上下文膨胀 | 响应慢或失败 | 摘要、窗口裁剪、工具输出压缩 |

## 18. Codex 执行规则

后续让 Codex 执行时，按以下规则：

1. 每次开始先 `git status --short`，确认未提交变更。
2. 只做当前阶段，不顺手做相邻重构。
3. 先补测试或至少明确验证入口。
4. 不复制参考项目源码。
5. 不写入真实 API Key。
6. 修改 docs 目录时文件名必须有中文描述。
7. Android 改动优先跑相关单测；涉及 UI/资源/构建配置跑 lint 或 assembleDebug。
8. Gateway 改动必须跑 `go test ./...`。
9. 跨端协议改动必须更新 fixture 并双端验证。
10. 不自动 commit、push、release，除非用户明确要求。
