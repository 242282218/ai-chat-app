# 聊天生图重构执行文档

日期：2026-06-10  
对象：原生 Android AI 聊天应用  
目标：完全收敛到稳定聊天和生图主线，清理仓库冗余，升级移动端美学和交互体验。  

## 1. 核心判断

当前项目的问题不是缺少功能，而是需要把已经完成的瘦身继续落实到仓库、文档、体验和组件层。现有 Android 主体已经具备可复用骨架：Kotlin、Jetpack Compose、Room、Koin、OkHttp、Provider 协议、聊天流式响应、图片生成历史和迁移测试。直接推倒重写会丢失这些已验证资产，并放大 Room 迁移和 Provider 协议回归风险。

本轮“完全重构”的定义：

- 保留已验证主路径：聊天、图片输入、图片生成、Provider 配置、本地历史、模型选择、隐私存储。
- 清理不可达边界：Gateway、工具调用、搜索、RAG、长期记忆、Skill、Agent workflow、语音、本地推理、角色卡和旧导入导出。
- 把 UI 从“可用的 Material 3 表单集合”提升为“安静、清晰、状态完整的移动 AI 工作台”。
- 不通过新增大功能制造复杂度；只围绕发送、生成、保存、分享、恢复失败这些真实任务优化。

## 2. 方案取舍

| 方案 | 内容 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A：二次收敛重构 | 保留现有 Android 架构，分阶段清理仓库残留、拆分大文件、统一体验和视觉系统。 | 风险低，可逐阶段验证，最大化复用已有测试和迁移。 | 需要严格防止“顺手加功能”。 | 推荐 |
| B：UI/UX 优先重构 | 先集中修改主题、组件、聊天和生图界面，再处理仓库残留。 | 用户可感知变化快。 | 旧文档和边界残留会继续影响后续判断。 | 可作为 A 的中段执行 |
| C：推倒重写 | 从新包结构和新 UI 开始重写主路径。 | 边界最干净。 | Room 升级、Provider 协议、图片存储、测试资产全部面临回归。 | 不推荐 |

执行采用方案 A。UI/UX 作为独立阶段推进，但不绕开核心边界清理。

参考资料来自 `docs/同类项目调研.md` 和本地 `参考项目/`。

| 项目 | 借鉴 | 不照搬 |

## 4. 美学和交互方向

参考 `D:\PROJECT_ZZZZZZZZZ\设计美学研究`：

- `design-core`：信息目标、层级、色彩角色、排版节奏、证据密度、状态表达。
- `mobile-design-knowledge`：小屏首屏任务、触控目标、底部导航、键盘遮挡、错误恢复、离线状态。
- 产品美学计划：Evidence-first、Behavior before visuals、Mobile is task flow。

目标设计语言：Quiet Native AI Workbench。

视觉约束：

- 内容和状态优先，禁止用抽象渐变、玻璃、装饰光效替代真实输出。
- 主背景保持中性，accent 只用于主行动、当前状态和能力识别。
- 避免整体被紫蓝色占满；聊天、图片、成功、警告、错误使用清晰语义色。
- 字级要服务移动扫读：页面标题、分组标题、正文、说明、标签稳定分层。
- 所有关键触控目标保持不小于 48dp。
- 空、加载、错误、离线、权限、失败重试都必须说明原因、影响和下一步。
- 动效只解释进入、离开、展开、完成、失败、等待；支持 reduced motion 等价体验。

核心证据：

- 聊天页展示真实消息、Provider/模型状态、流式状态、失败恢复。
- 生图页展示提示词、模型参数、生成状态、本地作品和可复用动作。
- 设置页展示连接状态、能力标签、密钥状态、请求端点预览和测试结果。

## 5. 目标架构边界

目标目录边界保持当前分层，不引入新大模块：

```text
app/          Application、Koin、Android 入口
data/         Room、DAO、entity、mapper、repository、SecretStore、ImageStorage
domain/       model、repository 接口、usecase
feature/      conversations、chat、image、provider
provider/     OpenAI / OpenAI-compatible 协议、模型发现、错误恢复
ui/           theme、component、markdown
navigation/   顶层导航和草稿交接
```

必须保持的边界：

- `data entity` 不泄漏到 `domain/feature`。
- UI 状态放在 ViewModel/UiState，Compose 只负责声明式渲染。
- Provider 能力只表达文本、视觉、图片，不恢复工具模型、代码模型和 Agent 能力。
- Room 旧迁移里的工具、记忆、提示词预设 SQL 是升级兼容资产，不是功能回流入口。
- 所有删除动作先确认没有运行时代码、测试、CI 或升级路径依赖。

- 记录当前测试基线和 git 状态，避免把已有问题误算成重构引入。

1. 读取 `README.md`、`docs/优化路线图.md`、`docs/同类项目调研.md`、`docs/基础架构与代码索引.md`。

### Phase 1：仓库和文档二次收敛

Spec：

- 仓库根目录只保留 Android App、测试、CI、发布和必要参考资料。
- `docs/` 文件名必须有中文描述；英文旧文档需要改名、合并或删除。
- `gateway/`、`contracts/gateway/` 若确认无文件和无 CI 引用，应删除空目录；若有真实文件，先写迁移/删除说明。
- 旧崩溃日志、replay 日志、CI 诊断日志不进入长期仓库资产。

Plan：

1. 删除空的 `gateway/`、`contracts/gateway/` 目录。
2. 处理根目录 `hs_err_pid*.log`、`replay_pid*.log`、`ci-android-*.log`，必要时补 `.gitignore`。
3. 将 `docs/ui-optimization-roadmap.md` 和 `docs/optimization-summary.md` 合并或改为中文文件名。
4. 清理 README、CHANGELOG 和 CI 中对 Gateway 的过期描述，只保留历史变更中必须保留的记录。
5. 更新 `docs/基础架构与代码索引.md`，确保当前入口与代码一致。

验收：

- `rg -n "Gateway|RAG|Skill|Agent workflow|sandbox" README.md docs app/src/main` 只剩“明确不做”或迁移兼容说明。
- `docs/` 下新增或保留文档文件名具备中文描述。
- 不删除 Room schema JSON 和迁移测试中的旧表测试数据。

### Phase 2：架构边界和大文件拆分

Spec：

- 不新增复杂模块系统，沿用 app/data/domain/feature/provider/ui 分层。
- 大文件拆分只围绕职责，不做抽象炫技。
- Provider 设置、生图页、通用组件应拆出可测试纯函数和小 Composable。

Plan：

1. `ProviderSettingsScreen.kt` 拆为列表、编辑表单、模型区域、连接测试、端点预览等文件。
2. `ImageGenerationScreen.kt` 拆为提示词输入、参数面板、状态提示、历史网格、历史详情动作。
3. `WorkbenchComponents.kt` 按基础控件、面板、状态、反馈拆分，保留对外命名稳定。
4. 对拆出的纯函数补或移动单测，优先覆盖验证、状态推导、能力标签。
5. 每次拆分只迁移一个文件族，避免同阶段大面积重命名。

验收：

- 单个 Composable 文件不再承担多个页面级职责。
- 纯逻辑继续在 `*Drafts.kt`、`*Options.kt` 或独立 state helper 中测试。
- `testDebugUnitTest` 和 `lint` 通过。

### Phase 3：Provider 和模型设置体验重构

Spec：

- 设置页定位为“模型连接”，不是杂项设置中心。
- 用户第一眼看到：可用 Provider、默认聊天模型、图片模型、密钥状态、连接健康。
- 高风险项如 HTTP、自定义 Header、Base URL 规范化进入高级区。
- 图片模型和聊天模型可独立选择，但必须共享清晰的 Provider 能力说明。

Plan：

1. 将底部“设置”文案调整为“模型”或在页面标题中明确“模型连接”。
2. Provider 列表使用能力标签：文本、视觉、图片。
3. 新增或强化连接摘要：启用状态、默认模型、模型数量、密钥状态、HTTP 风险。
4. 编辑流程按“基础信息 -> 密钥 -> 模型 -> 高级请求头/HTTP -> 测试”组织。
5. 错误恢复文案给出下一步：补 API Key、修 Base URL、同步模型、切换 Provider。

验收：

- 新用户能在 30 秒内知道如何配置聊天和生图 Provider。
- 保存、测试、模型发现按钮的 disabled/loading/error/success 状态完整。
- 不出现工具模型、代码模型、Agent 能力等过期概念。

### Phase 4：聊天主路径体验重构

Spec：

- 聊天页主任务是输入、发送、等待、取消、重试、继续对话。
- 会话列表主任务是找到旧会话或快速新建。
- 消息气泡必须兼顾 Markdown、图片输入、错误、流式中状态和长内容可读性。

Plan：

1. 会话列表空状态给出明确行动：新建聊天、配置模型。
2. 聊天页 TopBar 降低信息密度，Provider/模型状态使用轻量标签或详情入口。
3. 输入栏处理键盘、发送、生成中禁用、取消、错误保留草稿。
4. 消息气泡优化宽度、间距、角色识别、Markdown 代码块和图片预览。
5. 失败消息提供重试和打开模型连接入口。
6. 长对话压缩状态只作为系统能力提示，不暴露内部实现细节。

验收：

- 没有 Provider 时，用户能从聊天页进入配置并返回。
- 流式、取消、失败、重试不会丢失用户输入。
- 图片输入和图片引用不遮挡文本主路径。
- TalkBack 可识别发送、取消、复制、重试等动作。

### Phase 5：生图主路径体验重构

Spec：

- 生图页主任务是写提示词、选择模型、生成、查看本地作品、复用/保存/分享/转聊天。
- 参数默认值要清晰，不把高级参数压到首屏噪音里。
- 失败记录是有价值资产，应帮助用户重试，而不是只显示失败。

Plan：

1. 首屏以提示词输入和生成状态为焦点，参数面板默认折叠或分组。
2. 参数覆盖模型、尺寸、质量、数量，状态文案沿用 `ImageReadiness`。
3. 历史区展示作品缩略图、提示词摘要、状态、时间和主要动作。
4. 失败项提供“复用提示词”“调整参数”“打开模型连接”“发送到聊天分析失败”。
5. 保存/分享动作明确本地文件状态和失败原因。

验收：

- 没有图片 Provider、缺 API Key、模型不支持、数量无效都有明确恢复路径。
- 生成中可以取消；取消后的历史状态可理解。
- 作品库空状态和失败状态都指向下一步。
- 生图页不引入本地 Stable Diffusion 或额外运行时。

### Phase 6：视觉系统和交互动效统一

Spec：

- 以 Material 3 为基础建立项目级 token，而不是每个页面局部调色。
- 控件、间距、圆角、状态色和动效有统一规则。
- 视觉升级服务真实内容，不做营销页、装饰背景或不必要英雄区。

Plan：

1. 调整 `Theme.kt`：中性背景、清晰 primary、图片 accent、成功/警告/错误语义色；避免整体紫蓝化。
2. 定义间距和圆角使用规则：列表、面板、输入、图片缩略图、对话气泡分别约束。
3. 统一 `EmptyState`、`ErrorState`、`LoadingState`、`InlineNotice` 的语气和布局。
4. 增加状态转场：列表项、面板展开、生成状态、错误恢复；动效克制且可关闭。
5. 检查所有按钮和图标按钮：48dp、content description、tooltip 或可见文本。
6. 对 360dp、390dp、折叠屏/平板宽度做布局审查，避免文字溢出和控件重叠。

验收：

- 主路径页面截图能看出统一设计语言。
- 关键文本对比可靠，按钮/标签文字不溢出。
- 没有装饰性渐变、光斑、假数据和无意义大卡片。
- `lint` 和 `assembleDebug` 通过。

### Phase 7：回归、CI 和发布门禁

Spec：

- 每阶段合入前都有最小充分验证。
- 数据库和迁移变更必须更新 schema JSON 并跑迁移测试。
- 不因小 UI 调整发 GitHub Release；只有完整闭环或安装包修复才发布。

Plan：

1. 常规 Android 验证：

```powershell
.\gradlew.bat testDebugUnitTest lint assembleDebug --no-daemon --stacktrace
```

2. Room 相关变更追加：

```powershell
.\gradlew.bat testDebugUnitTest --tests "*AiChatMigrationTest*" --no-daemon --stacktrace
```

3. PR 或合并前跑 GitHub Actions Android workflow。
4. 需要真实设备、端口或外部 Provider 时，再使用测试机，并带回日志结论。
5. 发布前确认 APK 可安装；无正式签名配置时不发布 release APK。

验收：

- CI 绿色。
- 单测、lint、assembleDebug 至少完成一次全量回归。
- 若发布，Release notes 说明用户可感知变化、验证命令和安装包类型。
