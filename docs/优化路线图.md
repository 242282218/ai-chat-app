# AI Chat 项目优化路线图

> 生成日期：2026-06-01  
> 范围：Android Kotlin Compose 客户端 + Go Gateway  
> 方法：基于当前代码只读审查，并对标 RikkaHub、GPT Mobile、Chatbox、NextChat、LibreChat、Open WebUI、LobeChat、Now in Android 等开源项目。  
> 目的：明确下一阶段优化方向、优先级、关键文件、成功标准和验证方式。

## 1. 结论摘要

当前项目已经具备较完整的 AI Chat Workbench 雏形：原生 Android、Compose、Material 3、Room、本地优先数据、OpenAI/OpenAI-compatible Provider、图片生成、工具调用、长对话压缩、Koin 依赖注入、Baseline Profile 模块和基础 CI。

下一阶段不建议继续优先堆功能，而应先补强以下基础能力：

1. **发布阻断与安全底线**：补齐 Android 网络权限，收紧 Gateway 认证、监听地址、请求体大小和超时。
2. **密钥与 Header 安全**：Provider 自定义 header 不应靠 denylist 过滤，敏感 header 应走 SecretStore 或默认拒绝持久化。
3. **统一网络层**：统一 OkHttp client、timeout、取消、错误模型、User-Agent、request id、日志脱敏。
4. **Provider 一致性**：当前 descriptor/capability 已有雏形，但实际 ChatProvider 实现与 UI 可选项需要对齐。
5. **长会话性能**：消息观察和 UI 渲染应从全量列表演进到窗口化/分页。
6. **工程化发布**：补充 emulator smoke test、Gateway race test、依赖/安全扫描、签名和 release 产物可信度。

这些工作是后续 MCP、RAG、Agent、多 Provider、本地模型的前置地基。如果不先做，复杂功能会放大安全、性能和维护成本。

## 2. 当前项目现状

### 2.1 已具备能力

- Android App：Kotlin、Jetpack Compose、Material 3、Room、OkHttp。
- 依赖注入：Koin 组装数据库、Repository、Provider、Gateway、UseCase、ViewModel。
- Provider：OpenAI、OpenAI-compatible 文本聊天，OpenAI 图片生成；Provider descriptor 已覆盖 Anthropic、Gemini、Ollama、OpenRouter 等类型信息。
- Chat：流式输出、停止、重试、编辑重发、工具调用 loop、工具确认、长对话压缩。
- 本地数据：会话、消息、Prompt、模型偏好、Provider 配置、工具结果、图片历史。
- 隐私：API Key 通过 Android Keystore 支持的 SecretStore 保存；备份导出不包含 API Key。
- Gateway：健康检查、工具清单、搜索、Python 沙箱执行。
- 质量：基础单元测试、Room/Robolectric 测试、Android CI、Gateway CI、Baseline Profile 模块。

### 2.3 主要风险

1. **Android Manifest 缺少 `INTERNET` 权限**：真实设备上 Provider、图片生成和 Gateway 网络请求可能失败。
2. **Gateway 默认暴露面过大**：`/v1/search` 和 `/v1/sandbox/run` 缺少认证；默认监听 `:8080`，如果部署到公网或局域网会成为未授权执行入口。
3. **Gateway HTTP 硬化不足**：只设置了 `ReadHeaderTimeout`，缺少完整 timeout、body limit、并发/速率限制。
4. **Provider 自定义 headers 的敏感字段过滤不完整**：当前是 denylist，可能遗漏 `anthropic-api-key`、`x-goog-api-key`、`cookie`、`x-auth-token` 等字段，导致密钥进入 Room 和备份。
5. **网络层分散**：Provider、图片生成、Gateway、连接测试各自创建 OkHttpClient，timeout、取消、错误、脱敏不统一。
6. **Provider descriptor 与实际 client 支持不完全一致**：Anthropic/Gemini 等已有 descriptor，但未看到对应 ChatProvider 实现注册，存在运行期不可用风险。
7. **长会话全量加载**：消息 observe、Repository 映射、UI state 和 LazyColumn 都按全量消息处理，长会话性能风险明显。
8. **UI 状态收集未生命周期感知**：Compose screen 仍使用 `collectAsState()`，建议改为 `collectAsStateWithLifecycle()`。
9. **备份导入缺少更强约束**：需要 version 支持范围、文件大小、消息数量、字段长度、header 安全策略和 dry-run preview。
10. **发布工程仍偏基础**：缺少 emulator smoke test、Dependency Review、CodeQL、Gradle dependency verification、release signing/provenance/SBOM 等。

## 4. 优先级路线图

### Phase 0：工作区保护与发布阻断修复

**目标**：保护当前大量未提交变更，先修会阻断真实运行或带来高安全风险的问题。

**动作**：

1. 每次实施前确认 `git status`，避免覆盖已有未提交变更。
2. Android Manifest 顶层添加：

   ```xml
   <uses-permission android:name="android.permission.INTERNET" />
   ```

3. Gateway 默认监听从 `:8080` 改为 `127.0.0.1:8080`。
4. Gateway 增加 `GATEWAY_API_TOKEN`，保护 `/v1/search` 和 `/v1/sandbox/run`。
5. Gateway 增加 body limit、完整 timeout、sandbox code length limit。
6. Provider custom headers 改为 allowlist 或 SecretStore 化，停止依赖敏感字段 denylist。

**关键文件**：

- `app/src/main/AndroidManifest.xml`
- `gateway/internal/config/config.go`
- `gateway/cmd/gateway/main.go`
- `gateway/internal/httpapi/server.go`
- `app/src/main/java/com/aichat/workbench/tool/gateway/GatewayClient.kt`
- `app/src/main/java/com/aichat/workbench/data/repository/RoomProviderConfigRepository.kt`
- `app/src/main/java/com/aichat/workbench/data/backup/AppBackupService.kt`

**成功标准**：

- Release/debug APK 均包含 `INTERNET` 权限。
- Gateway 默认不对外网卡开放。
- 无 token 请求 Gateway 敏感接口被拒绝。
- 超大 body 返回明确错误，不消耗大量内存。
- 敏感 header 不进入 Room `headers_json`，也不进入备份 JSON。

**验证**：

```powershell
.\gradlew.bat testDebugUnitTest lint assembleDebug assembleRelease --no-daemon --stacktrace
```

```powershell
cd gateway
go test ./...
go vet ./...
```

新增/补充测试：

- Manifest 权限 smoke test。
- Gateway auth/body limit/timeout 测试。
- Header 敏感字段测试：`anthropic-api-key`、`x-goog-api-key`、`cookie`、`x-auth-token` 不应被持久化或导出。

### Phase 1：统一网络层与错误模型

**目标**：让 OpenAI、OpenAI-compatible、图片生成、Gateway、连接测试的超时、取消、错误、日志脱敏一致。

**现状**：

多个类默认各自创建 `OkHttpClient()`：

- `OpenAiChatProvider`
- `OpenAiImageGenerationProvider`
- `GatewayClient`
- `ProviderConnectionTester`

这会导致 timeout、SSE 策略、取消、User-Agent、request id、错误映射和日志脱敏无法统一。

**推荐设计**：

1. 新增统一 network provider/factory，由 Koin 提供：
   - short JSON client
   - streaming SSE client
   - image generation client
   - gateway client
2. 统一配置：
   - `connectTimeout`
   - `readTimeout`
   - `writeTimeout`
   - `callTimeout`
   - User-Agent
   - X-Request-Id
   - Authorization/API key/custom secret header 脱敏
3. 定义统一错误模型：
   - auth failed
   - rate limited
   - model not found
   - timeout
   - network unavailable
   - malformed response
   - unsupported capability
4. 明确 `GenerationController.stop()` 取消 coroutine 时底层 OkHttp `Call` 会关闭。

**关键文件**：

- `app/src/main/java/com/aichat/workbench/app/AppModule.kt`
- `app/src/main/java/com/aichat/workbench/provider/openai/OpenAiChatProvider.kt`
- `app/src/main/java/com/aichat/workbench/provider/compatible/OpenAiCompatibleChatProvider.kt`
- `app/src/main/java/com/aichat/workbench/provider/image/OpenAiImageGenerationProvider.kt`
- `app/src/main/java/com/aichat/workbench/tool/gateway/GatewayClient.kt`
- `app/src/main/java/com/aichat/workbench/provider/api/ProviderConnectionTester.kt`
- `app/src/main/java/com/aichat/workbench/provider/http/SseParser.kt`

**成功标准**：

- 所有 HTTP 调用经统一 client/factory。
- UI 错误提示一致，能区分认证失败、限流、模型不存在、网络超时等。
- secret 不进入日志。
- stop generation 能及时取消底层请求。

**验证**：

- MockWebServer 覆盖 streaming、timeout、malformed SSE、401、429、5xx、cancellation。
- 手工验证弱网、取消生成、Provider key 错误、模型不存在。

### Phase 2：Provider descriptor 与实际能力一致

**目标**：让 Provider 配置、连接测试、Chat 主路径和 UI 展示只暴露真实可用能力。

**现状**：

`ProviderDescriptor`、`ProviderProtocol`、`ModelCapability` 已有较好雏形，但实际注册的 ChatProvider 主要是 OpenAI/OpenAI-compatible。Anthropic/Gemini 等 descriptor 如果被 UI 允许选择，发送时可能遇到运行期 `No ChatProvider registered`。

**推荐设计**：

1. `ProviderRegistry` 明确区分：
   - all descriptors
   - registered chat providers
   - displayable providers
   - coming soon descriptors
2. Provider 设置 UI 只展示已注册且可用的 provider；未实现的类型标记为暂不可用或隐藏。
3. ProviderConnectionTester 和 Chat 入口统一使用注册状态与 capability 检查。
4. 后续新增 Provider 时按代表性推进：
   - OpenRouter：复用 OpenAI-compatible，低成本覆盖多模型。
   - Anthropic：验证非 OpenAI 协议。
   - Gemini：验证多模态和不同错误模型。
   - Ollama：验证 local/no-api-key 场景。

**关键文件**：

- `app/src/main/java/com/aichat/workbench/domain/model/ProviderConfig.kt`
- `app/src/main/java/com/aichat/workbench/provider/ProviderRegistry.kt`
- `app/src/main/java/com/aichat/workbench/provider/api/ChatProvider.kt`
- `app/src/main/java/com/aichat/workbench/provider/api/ProviderConnectionTester.kt`
- `app/src/main/java/com/aichat/workbench/feature/provider/ProviderDrafts.kt`
- `app/src/main/java/com/aichat/workbench/feature/provider/ProviderSettingsScreen.kt`
- `app/src/main/java/com/aichat/workbench/feature/chat/GenerationController.kt`

**成功标准**：

- UI 不展示不可用 provider，或明确标记不可用。
- 新 Provider 不需要修改 Chat 主流程。
- Provider/model 不支持的功能不会在 UI 中出现。
- Ollama/no-api-key provider 能自然工作。
- 连接测试能根据协议和认证方式差异处理。

**验证**：

- `ProviderRegistryTest`
- `ProviderDraftsTest`
- `ProviderConnectionTesterTest`
- MockWebServer 覆盖 200/401/404/429/5xx、非标准错误体、不同 `/models` 返回。

### Phase 3：长会话性能与状态体验

**目标**：补齐长会话打开、滚动、流式写库、自动滚动和生命周期状态收集体验。

**现状**：

当前消息列表从 DAO observe 到 Repository 映射、ViewModel state、LazyColumn 渲染都是全量消息。长会话、图片消息、Markdown 代码块和流式生成会放大性能成本。

**推荐设计**：

1. 消息列表先做窗口化，不急着上 Paging 3：
   - `observeRecentMessages(conversationId, limit = 80)`
   - `loadMessagesBefore(conversationId, beforeCreatedAt, limit = 50)`
2. UI state 增加：
   - `hasMoreBefore`
   - `isLoadingMore`
   - `oldestLoadedMessageTime`
3. Chat UI 滚动策略：
   - 用户在底部时自动滚动。
   - 用户已上滑时不打断，显示“跳到最新”。
4. 屏幕层使用 `collectAsStateWithLifecycle()`。
5. 一次性事件用 `SharedFlow`/Channel，避免 copy/share/snackbar/error 被长期 UI state 重复消费。
6. 保持 final message 必须落库；流式 delta 可以继续节流写库。

**关键文件**：

- `app/src/main/java/com/aichat/workbench/feature/chat/ChatViewModel.kt`
- `app/src/main/java/com/aichat/workbench/feature/chat/GenerationController.kt`
- `app/src/main/java/com/aichat/workbench/feature/chat/ConversationCompactor.kt`
- `app/src/main/java/com/aichat/workbench/feature/chat/ChatScreen.kt`
- `app/src/main/java/com/aichat/workbench/domain/usecase/SendMessageUseCase.kt`
- `app/src/main/java/com/aichat/workbench/data/local/dao/ConversationDao.kt`
- `app/src/main/java/com/aichat/workbench/data/repository/RoomConversationRepository.kt`

**成功标准**：

- 1000+ 消息会话可稳定打开和滚动。
- 长流式回复不卡顿。
- Room 写入次数受控。
- stop/retry/edit/tool calling 行为不回归。
- 用户上滑阅读时不会被强制拉到底。

**验证**：

- `ChatViewModelTest`
- `GenerationControllerTest`
- `ConversationCompactorTest`
- 构造 1000/5000 消息会话 JVM/Robolectric 测试。
- 后续补 Macrobenchmark：冷启动、进入 Chat、打开长会话、长回复 streaming。

### Phase 4：工具调用与 Gateway 能力强化

**目标**：让 Gateway 工具从“可调用”变成“安全、可追溯、体验稳定”的聊天主路径能力。

**推荐设计**：

1. `ToolExecutor` 缓存 Gateway manifest：
   - TTL 1-5 分钟。
   - Gateway settings 变化时失效。
   - Tools 页面手动刷新。
2. `descriptorFor()` 不应每次重新拉远程 manifest。
3. Tool result UI 结构化渲染：
   - `web_search`：title/url/snippet/source/publishedAt 卡片。
   - `code_sandbox`：stdout/stderr/exitCode 可展开。
4. 工具权限策略细化：
   - read-only
   - network
   - file read/write
   - execute
   - sensitive/destructive
5. 搜索失败不允许模型编造来源。
6. 长期再考虑 MCP，不急着做插件市场。

**关键文件**：

- `app/src/main/java/com/aichat/workbench/feature/chat/GenerationController.kt`
- `app/src/main/java/com/aichat/workbench/feature/chat/ToolExecutor.kt`
- `app/src/main/java/com/aichat/workbench/tool/gateway/GatewayClient.kt`
- `app/src/main/java/com/aichat/workbench/tool/model/ToolManifest.kt`
- `app/src/main/java/com/aichat/workbench/data/repository/RoomToolInvocationRepository.kt`
- `gateway/internal/search/search.go`
- `gateway/internal/search/searxng.go`
- `gateway/internal/httpapi/server.go`

**成功标准**：

- 聊天中至少一个真实搜索工具闭环可用。
- 工具调用有持久化记录和可视状态。
- 搜索结果可追溯，失败不编造来源。
- 需要确认的工具必须弹确认。
- Gateway manifest 不在一次 generation 中被重复拉取。

**验证**：

- `GatewayClientTest`
- `ToolExecutorTest`
- `GenerationControllerTest`
- Gateway：`go test ./...`
- 本地 SearXNG 或 mock server 端到端 smoke test。

### Phase 5：备份、隐私与本地数据安全

**目标**：保证用户能理解数据流，敏感信息默认不泄露，备份导入导出可控可恢复。

**推荐设计**：

1. 备份导出：
   - 默认不含 API key。
   - 默认不含敏感/临时会话。
   - Provider headers 再次脱敏。
   - schemaVersion/appVersion 明确。
2. 备份导入：
   - version 支持范围校验。
   - 文件大小限制。
   - conversation/message 数量上限。
   - 单条 message/toolResult 字段长度上限。
   - provider headers 安全过滤。
   - dry-run preview。
3. 高隐私模式：
   - API Key 页面可选 `FLAG_SECURE`。
   - 敏感会话禁截图/录屏。
   - 最近任务隐藏敏感内容。
   - 复制到剪贴板时提示；Android 13+ 可标记 sensitive clipboard。
4. 高阶可选：
   - SQLCipher/数据库加密。
   - 生物识别解锁 API Key 或敏感会话。
   - 加密备份。

**关键文件**：

- `app/src/main/java/com/aichat/workbench/data/backup/AppBackupService.kt`
- `app/src/main/java/com/aichat/workbench/data/crypto/AndroidSecretStore.kt`
- `app/src/main/java/com/aichat/workbench/data/local/AiChatDatabase.kt`
- `app/src/main/java/com/aichat/workbench/feature/provider/ProviderSettingsScreen.kt`
- `app/src/main/java/com/aichat/workbench/feature/settings/DataSettingsScreen.kt`
- `README.md`

**成功标准**：

- 备份 JSON 不含 API key 或敏感 header。
- 恶意/异常大备份不会导致 OOM 或卡死。
- 用户导入前能看到将导入的数据摘要。
- 用户能理解哪些数据本地保存，哪些会发往 Provider/Gateway。

**验证**：

- Backup export/import 单测。
- 超大 backup/fuzz-like 样例测试。
- 手工检查导出 JSON。
- 设置页/README 隐私说明审查。

### Phase 6：CI、Release 与供应链可信度

**目标**：补齐正式发布可信度和供应链安全基线。

**推荐设计**：

1. Android CI：
   - `testDebugUnitTest`
   - `lint`

## 5. 长期方向

### 5.1 MCP Gateway Proxy

推荐 Android 不直接管理 MCP server 生命周期，而是交给 Go Gateway。App 只消费 manifest、展示权限、执行 tool call、持久化结果。

启动条件：

- Chat-integrated tool calling 稳定。
- Gateway 认证、权限、审计模型明确。
- Tool schema/result schema 稳定。

### 5.2 文件输入、总结、轻量 RAG

推荐顺序：

1. TXT/MD 文本抽取。
2. PDF 文本抽取。
3. 单文件总结。
4. 会话附件引用。
5. 长会话 summary memory 可编辑。
6. 多文件索引/RAG。

不建议立即做完整 RAG，因为 embedding、索引、召回、重排、引用、权限和存储都会显著增加复杂度。

### 5.3 本地模型 / GGUF

先做 Ollama / LM Studio / OpenAI-compatible local endpoint，不建议立即内置 llama.cpp/GGUF 推理。

原因：内置推理涉及包体、设备兼容、电量、温控、模型下载和量化管理，成本高。

### 5.4 渐进式 Gradle 模块化

当前包分层还可维护，短期不建议一次性大拆。等 Provider/tool/chat 边界稳定后，按收益逐步拆：

1. `:core:model`
2. `:core:network`
3. `:core:security`
4. `:core:database`
5. `:core:ui`
6. `:feature:chat`
7. `:feature:provider`
8. `:feature:tools`
9. `:provider:openai`
10. `:provider:anthropic`
11. `:provider:gemini`

先拆 `core:model`、`core:network`、`core:security` 最划算，避免 feature 直接依赖 data 实现。

## 6. 不建议立即做的方向

1. **复杂插件市场**：先稳内部 tool interface、permission、result rendering，再扩 MCP/plugin。
2. **完整 RAG**：应先完成搜索、文件总结、上下文压缩和引用渲染。
3. **复杂 Agent workflow**：tool calling、权限、审计、取消、重试还需先稳定。
4. **内置 GGUF 推理**：先用 Ollama/LM Studio 低成本验证 local model UX。
5. **一次性支持所有 Provider**：先让 descriptor 与实际实现一致，再接 OpenRouter/Anthropic/Gemini/Ollama 四类代表。
6. **大规模多模块拆分**：当前工作区变更多，边界仍在演进，容易制造冲突。
7. **重量级 Markdown 全家桶**：先补链接、代码块、表格、复制和性能；Mermaid/LaTeX 后置。

## 7. 最小高价值落地组合

如果只做一轮优化，推荐按这个顺序：

1. Android `INTERNET` 权限。
2. Gateway 认证、loopback 默认、body limit、完整 timeout。
3. Provider custom headers 改 allowlist/SecretStore，备份导出二次脱敏。
4. 统一 OkHttp client、错误模型、取消行为、secret 脱敏。
5. Provider descriptor 与实际 ChatProvider 支持对齐。
6. Chat 长会话窗口化 + `collectAsStateWithLifecycle()`。
7. Tool manifest 缓存 + 工具结果结构化 UI。
8. Android emulator smoke test + Gateway `go test -race` + Dependency Review/CodeQL。

### 8.3 自动化测试重点

- Manifest：release/debug manifest 包含 `INTERNET`。
- Provider：registry、descriptor availability、capability、connection tester、MockWebServer。
- Secret/Header：敏感 header 不进 Room/backup/log。
- Chat：send/retry/edit/stop、tool call loop、long context compaction、stream write throttling、cancellation。
- Data：Room migrations、backup export/import exclusion、backup size/version limit。
- Gateway：auth、body limit、timeout、search adapter、sandbox limits、manifest contract。
- UI：Chat empty/error/generating、Provider form、Tools permission dialog、Markdown code block、长会话滚动。

### 8.4 手工验收

1. 新装 App，配置 OpenAI/OpenAI-compatible Provider。
2. 发送普通消息、图片消息、停止生成、重试失败、编辑重发。
3. 打开 1000+ 消息会话，验证滚动和生成期间 UI。
4. 启动 Gateway，验证 token、搜索工具、sandbox 工具、错误提示。
5. 导出备份，确认不含 API key、敏感 header，不含默认排除的敏感/临时会话。
6. 导入异常 backup，确认不会卡死/OOM，能给出明确错误。
7. 安装 release APK，验证启动、Provider、Chat、Tools 主路径。
8. 检查 release APK checksum 和签名指纹。

## 9. 执行纪律

- 每个阶段单独提交，避免混合重构和功能。
- 优先修根因，不用 workaround 掩盖结构问题。
- 优先补测试，再扩展功能。
- 数据库 schema、Manifest、CI、release 配置单独提交。
- 不批量格式化无关文件。
- 不覆盖已有未提交变更。
- 每个阶段必须有最小充分验证。
- 涉及密钥、备份、网络权限、Gateway 暴露面的改动必须单独审查。
